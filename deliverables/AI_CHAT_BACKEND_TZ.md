# ТЗ: DeepSeek для AI-помощника ПНП

## Результат

Нужен отдельный `POST /api/ai-chat/`, который ведёт диалог с DeepSeek и возвращает ответ вместе со структурированным черновиком заявки. Этот endpoint не создаёт `Lead` и ничего не отправляет в Bitrix.

Пользователь сам подтверждает готовый черновик. После подтверждения фронт отправляет его в существующий `POST /api/catalog-request/`, поэтому обычная форма, чат с менеджером и AI используют один путь создания заявки.

## Где писать

- `main/ai.py`: работа с DeepSeek, prompt, очистка истории и разбор ответа.
- `main/views.py`: Django view `ai_chat_api`, HTTP-валидация, rate limit и преобразование ошибок в JSON.
- `main/urls.py`: маршрут `path("api/ai-chat/", views.ai_chat_api, name="api_ai_chat")`.
- `.env.example`: названия переменных без реального ключа.
- `main/tests.py`: тесты view с подменённым вызовом DeepSeek.

Для первого варианта новая библиотека не обязательна: можно использовать `urllib.request`, как уже сделано в `main/bitrix.py`. Если добавлять клиентскую библиотеку, её нужно зафиксировать в `requirements.txt`.

## Переменные окружения

```env
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-chat
DEEPSEEK_TIMEOUT_SECONDS=25
```

Ключ читается только на сервере. Его нельзя передавать в Django context, HTML, JavaScript, JSON-ответ или логи.

## Запрос от фронта

`Content-Type: application/json`, обычный Django CSRF обязателен.

```json
{
  "message": "Нужны минеральные потолочные панели, 800 м2, объект Москва",
  "history": [
    {"role": "user", "content": "Нужны потолочные панели"},
    {"role": "assistant", "content": "Какая площадь и где находится объект?"}
  ],
  "lead_draft": {
    "direction": "Архитектурные решения",
    "category": "Потолочные системы",
    "object": "",
    "message": "Минеральные потолочные панели, количество уточняется"
  },
  "catalog_items": [
    "Потолки|Потолочные системы|Минеральные потолочные панели"
  ],
  "page": "/catalog/"
}
```

Сервер не доверяет ограничениям фронта и повторно проверяет:

- `message`: обязательная строка, максимум 2000 символов;
- `history`: максимум 10 последних сообщений;
- `role`: только `user` или `assistant`;
- `content`: максимум 900 символов на сообщение;
- `lead_draft`: только известные строковые поля с собственными лимитами;
- `catalog_items`: максимум 30 строк, максимум 800 символов каждая;
- `page`: только путь, максимум 200 символов.

## Успешный ответ

```json
{
  "ok": true,
  "provider": "deepseek",
  "model": "deepseek-chat",
  "answer": "Зафиксировал панели, объём 800 м2 и объект в Москве. Какой срок поставки нужен?",
  "ready": true,
  "lead_draft": {
    "direction": "Архитектурные решения",
    "category": "Потолочные системы",
    "object_name": "Москва",
    "message": "Минеральные потолочные панели, 800 м2, объект в Москве. Срок поставки требуется уточнить.",
    "missing_fields": ["срок поставки"]
  }
}
```

Фронт также понимает старые имена `leadDraft`, `object` и `missingFields`, но новый backend должен возвращать snake_case.

## Что должен делать DeepSeek

В system prompt зафиксировать следующие правила:

- отвечать по-русски как спокойный B2B-консультант по комплектации объектов;
- помнить историю и не спрашивать повторно уже известные данные;
- определить направление, объект/город, позиции, количество, характеристики, срок, логистику и необходимость аналогов;
- задавать за один ответ один самый важный уточняющий вопрос;
- обновлять предыдущий черновик, а не создавать новый при каждом сообщении;
- понимать исправления: «не 800, а 1000», «убери кирпич», «оставь только панели»;
- сохранять единицы пользователя: штуки, м2, м3, тонны, паллеты, машины;
- не обещать цену, наличие, срок, сертификаты или совместимость без проверки менеджером;
- не выдумывать производителей и статус официального представителя;
- не сообщать, что заявка уже отправлена: её отправляет только пользователь;
- не возвращать HTML или Markdown;
- вернуть только JSON заданной структуры.

Для DeepSeek включить JSON output (`response_format: {"type": "json_object"}`). Слово `json` и пример требуемой структуры должны присутствовать в prompt. Даже после этого ответ нужно разбирать через `json.loads()` и валидировать каждое поле.

## Ответственность функций

Рекомендуемое разбиение без смешивания HTTP и бизнес-логики:

- `normalize_ai_history(value)`: фильтрует роли, длину и число сообщений.
- `normalize_lead_draft(value)`: оставляет только разрешённые поля и обрезает строки.
- `build_ai_messages(message, history, draft, catalog_items, page)`: создаёт system/user messages для DeepSeek.
- `call_deepseek(messages)`: читает env, делает запрос с таймаутом и возвращает текст ответа модели.
- `parse_ai_result(text)`: разбирает JSON, проверяет `answer` и нормализует `lead_draft`.
- `ai_chat_api(request)`: проверяет метод, CSRF, JSON и rate limit, вызывает функции выше и формирует `JsonResponse`.

## Ошибки

- `400`: пустое сообщение или некорректный JSON.
- `429`: превышен лимит запросов.
- `502`: DeepSeek недоступен, вернул ошибку или невалидный JSON.
- `503`: `DEEPSEEK_API_KEY` не настроен.

Формат ошибки:

```json
{
  "ok": false,
  "error": "ai_unavailable",
  "error_message": "AI-помощник сейчас недоступен. Можно перейти во вкладку «Менеджер»."
}
```

Не возвращать пользователю исходный текст исключения, ответ провайдера, prompt или детали ключа.

## Безопасность

- Rate limit хранить через Django cache, а не в обычном словаре процесса. Стартовый предел: 20 сообщений с одного IP за 10 минут.
- Поставить таймаут внешнего запроса и ограничить максимальный размер ответа.
- Не логировать полные сообщения, телефон, email и весь черновик. В логах достаточно request id, статуса, времени и типа ошибки.
- Ответ модели считать недоверенными данными и повторно обрезать все поля.
- Не давать модели возможность самостоятельно вызывать Bitrix или создавать `Lead`.
- Файлы пока не отправлять в DeepSeek. Они прикладываются только к финальной заявке и уходят менеджеру через существующий безопасный upload-путь.
- Перед production обновить версию политики/согласия и отдельно проверить юридические основания передачи сообщений внешнему AI-провайдеру.

## Минимальные тесты

1. Пустое сообщение возвращает `400`, DeepSeek не вызывается.
2. История с неизвестными ролями и слишком длинными строками очищается.
3. Успешный ответ DeepSeek возвращает `answer` и нормализованный `lead_draft`.
4. Исправление «не 800, а 1000 м2» обновляет существующий черновик.
5. Невалидный JSON модели возвращает безопасный `502`.
6. Отсутствующий ключ возвращает `503` без утечки конфигурации.
7. Rate limit возвращает `429`.
8. AI endpoint не создаёт `Lead` и не вызывает `send_lead_to_bitrix`.
9. Финальная отправка AI-черновика через `/api/catalog-request/` создаёт один `Lead` с `source=ai_chat`.
