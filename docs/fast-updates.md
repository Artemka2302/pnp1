# Быстрые обновления PNP1

Этот проект — Django pnp1.ru, не старый Node/proleas.ru. Повторно искать сервер,
ветки, ключ, логотипы и команды не нужно. Сверять текущее состояние всё равно нужно.

## Обычный цикл

1. Проверить git status; изменить только файлы задачи. Материалы производителей:
   data_import/solutions.json, существующий логотип, оригинальные PDF в static/assets/solutions.
2. tools/build_solution_assets.py теперь переиспользует страницы и обложки по SHA256.
   Новые/изменённые PDF обрабатываются; --rebuild нужен только для полной пересборки.
3. Выбрать минимальную проверку по таблице ниже. Не запускать release-pnp.ps1
   для каждой локальной правки: это консервативный релизный сценарий.
4. Браузер открывать только по условиям ниже; не повторять неизменённые проверки.
5. После отдельного запроса на пуш/деплой: проверить diff, закоммитить только файлы задачи,
   выполнить `./tools/release-pnp.ps1 -Deploy -GitProxy http://127.0.0.1:10809 -SmokePath /solutions/iss/`.
   Прокси указывать только если этот локальный прокси действительно работает.

Скрипт проверяет чистоту локального и серверного checkout, тесты, отсутствие
опасных файлов, fast-forward обеих веток, собирает web, отключает миграции,
обновляет статику без очистки, перезапускает только web, проверяет health и целевую
страницу. При неудачном переключении восстанавливает предыдущий образ и его статику.
Никакого force push, автоматического коммита, удаления файлов или редактирования .env.

## Экономный режим по умолчанию (согласован 15.10.2026)

Проверяем изменение, а не весь сайт. Рабочий production — основание переиспользовать
неизменённый шаблон, но новые пути/данные и результат публикации всё равно проверяем.
Перед работой определить затронутые файлы и достаточный признак успеха; после его
получения остановиться. Не добавлять улучшения, инфраструктуру и тесты вне задачи.

| Изменение | Достаточная проверка по умолчанию | Браузер |
| --- | --- | --- |
| Только инструкции/документация | Diff, ссылки; валидатор изменённого skill | Нет |
| Обычный текст/ссылка в готовом шаблоне | Diff + нужный текст/URL в одном HTTP-ответе или существующий точечный тест | Нет; исключение — риск переполнения длинным текстом |
| PDF/бренд по готовой схеме, без изменения логики | Валидность новых записей, пути/файлы, инкрементальная сборка; новые маршруты и привязки одним пакетным smoke | Не по умолчанию; новый логотип/фон сначала проверить локально |
| CSS/верстка/новый компонент | Соответствующий тест при наличии + затронутый блок desktop/mobile | Одна репрезентативная страница, обычно 2 снимка на пакет |
| JS/интерактивность | Тест изменённого поведения и один необходимый пользовательский сценарий | Только этот сценарий |
| Изолированная Python-функция/команда | Тесты этой функции/модуля; Django check, если затронута конфигурация приложения | Только при UI-риске |
| Авторизация, БД/миграции, зависимости, общая маршрутизация, CRM/AI, широкий рефакторинг | Расширить проверки по конкретным зависимостям; полный suite при широком влиянии/неясной области регрессии | По затронутому поведению |

Выбирать существующий небольшой тест или HTTP-smoke, не оба без разных рисков.
Для нового адресного sync достаточно main.test_solution_vendors, а не всех main.
Для библиотеки решений использовать релевантные методы main.test_solutions;
весь модуль — если изменился её общий контракт. Не писать тесты на каждое слово текста.

### Терминал, вывод и повторное использование

- HTTP через терминал проверяет статус, редирект, серверный текст, href/src и файлы.
  Проверять ожидаемое содержимое, не только 200. Ссылки проверять только новые/изменённые.
  HTTP не доказывает работу JS, клика, адаптивности или внешний вид.
- Для необходимого UI использовать доступный браузерный инструмент, не имитацию мыши
  через shell и не обход правил браузера. Предпочитать DOM-локаторы координатам.
- Один пакет проверок, вывод: число OK и конкретные ошибки. Не печатать HTML страниц,
  все тексты PDF, огромные DOM-деревья и успешные логи. Подробный лог — файл при необходимости.
- Не читать повторно уже прочитанные инструкции в том же контексте. Читать лишь нужные
  модули/ресурсы; обязательные выбранные skill-файлы читать полностью.
- Не использовать субагентов для рутинных правок. Не открывать браузер «на всякий случай».
- После ошибки исправить причину и повторить только затронутую проверку.
  Успех уже проверенного блока действителен, пока его код/данные/окружение не изменились.
- При браузерном таймауте — максимум одна обоснованная попытка восстановления;
  затем указать ограничение. Не тратить цикл на разные инструменты с тем же результатом.
- Обновления пользователю короткие; итог: что готово, существенные проверки, что не опубликовано.
  Скриншоты и отчёты не создавать без пользы или обязательного требования инструмента.
- Для незавершённой работы достаточно короткой заметки done/next/blocker/проверенный SHA
  и команды. Не переписывать историю проекта при каждом продолжении.

### PDF и публикация

- Старые неизменённые PDF не перечитывать/перерендеривать. Проверять только новые хеши.
- Сжатие: не перезаписывать оригинал; сравнить страницы, геометрию, текст и размер.
  Визуальную проверку новых PDF объединять в контактные листы; крупный план — для
  мелкого текста/схем или подозрительных страниц. Соблюдать обязательный PDF skill.
- На готовом просмотрщике не повторять ручное открытие каждого документа без причины:
  проверить новые маршруты/файлы пакетно; взаимодействие — если менялся просмотрщик.
- Перед релизом использовать действующие защитные проверки release-pnp.ps1 один раз;
  не запускать тот же suite вручную перед скриптом. Не добавлять skip-tests, не снимать
  блокировки критичных файлов, не обходить отсутствие резервной копии/разрешения.
- После публикации: SHA/health + целевые URL/статика. Визуально не обходить весь сайт,
  если не менялись общие стили/верстка. Локальный успех не заменяет production smoke.
- Успешные проверки переиспользовать по проверенному состоянию, не по фразе «раньше работало».

## Когда быстрый сценарий не подходит

### Новые бренды и тяжёлые PDF

- Для сжатия отдельной веб-копии: `python tools/optimize_solution_pdf.py SOURCE DESTINATION --dpi 150`.
  Нужны Ghostscript и pypdf. Оригиналы и существующие назначения не перезаписываются.
  Проверяются страницы, геометрия и извлечённый текст; изображения проверить визуально.
- После наполнения solutions.json выполнить инкрементальный tools/build_solution_assets.py.
- Новый бренд требует vendors_master.csv, catalog_vendor_map.csv и partners.json.
  Публичный partner.note содержит описание компании, а происхождение логотипа —
  logo_source_url, внутренние vendor.notes и документ задачи (не текст карточки).
- `python manage.py sync_solution_vendors --slugs BRAND1 BRAND2` — проверка без записи;
  `--apply` адресно обновляет только эти бренды, карточки партнёров и указанные связи.
  Не запускать полный import_pnp_data для добавления пары брендов.
- Web-only deploy не переносит записи БД. Production sync требует отдельной проверки
  выбранных брендов, резервной копии БД и разрешения на публикацию.
- Локальный сервер кеширует JSON: после изменения реестра перезагрузить dev-процесс,
  если новые страницы отвечают 404. Не путать это с отсутствующими данными в файле.
- Пример и размеры: docs/lift-solutions-2026-10-15.txt.

Критичные изменения БД, конфигурации, зависимостей, авторизации и интеграций требуют
оценки влияния и соответствующих расширенных проверок. При отказе релизного скрипта
использовать согласованный ручной сценарий; не обходить его защитные ограничения.
Локальные проверки выбирать по таблице выше, а не назначать полный аудит всему проекту.
Для новых PDF дополнительно проверить оригиналы, файлы и целевой маршрут;
не перескачивать все старые PDF после каждой текстовой/CSS-правки.

Объём тестов определяет таблица экономного режима, а не расширение файла.
Не повторять ту же матрицу без изменения соответствующего кода или окружения.
Production-тестовую БД не создавать.

.env не меняется: при следующих Compose up/recreate явно передавать APP_IMAGE_TAG
с SHA последнего релиза. Обычный docker restart сохраняет текущий образ.
Сохранённый предыдущий образ не удалять; git rollback и откат БД автоматически не делаются.

Скрипты проверены локально и в режиме валидации; универсальный сценарий пока не
применялся к production. Первый реальный запуск сопровождать и проверить результат.
